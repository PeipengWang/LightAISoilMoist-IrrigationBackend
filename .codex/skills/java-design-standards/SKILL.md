# 设计规范

本项目以小型 Spring Boot 后端为主，设计目标是清晰、可演进、容易测试。不要套用过重架构；也不要把所有逻辑堆进 Controller 或静态配置类。

## 分层边界

- Controller：HTTP 路由、参数绑定、状态码/响应封装。
- Service：业务规则、事务边界、参数语义校验、组合 Repository 和外部客户端。
- Client/Manager：OneNET、MQTT、文件存储等外部或基础设施能力的封装。
- Repository：只负责数据访问，不放业务规则。
- DTO/VO：表达 API 契约，不直接把实体对象暴露成长期稳定接口，除非是内部原型接口且影响范围明确。

当一个 Controller 方法开始处理类型转换、业务权限、第三方接口结果判断、日志落库时，应拆到 Service。

## 设计取舍

- 优先小步重构，不为单个需求引入复杂框架或抽象。
- 对设备属性、阈值类型、决策类型、错误类型这类有限集合，优先使用 enum 或集中常量，避免散落字符串。
- 对第三方平台响应，先在 Client 层转成项目内部对象或错误模型，再给 Service 使用。不要让 Controller 直接理解第三方响应结构。
- 对上传文件、SSE、MQTT、外部 API 等高风险边界，设计时明确失败行为、超时、重试和日志。
- 业务数据结构变化要同步更新文档、初始化数据和测试。

## 可扩展边界

- 新增设备或属性时，避免复制整段判断逻辑。设备元数据应集中维护，并提供查询方法。
- 新增接口时先定义请求/响应模型，再写 Controller。
- 新增存储字段时，同时考虑初始化数据、历史兼容、查询索引和默认值。
- 新增外部调用时必须有超时设置，并把第三方错误转成项目可理解的错误。

## 不建议的做法

- 在 Controller 中直接 new Thread、直接操作 Repository 完成复杂查询、直接拼响应 Map。
- 为了“未来可能用到”提前做复杂抽象。
- 在全局静态类里继续堆设备密钥、业务规则和展示文案。
- 用注释替代清晰的类/方法边界。

## 评审重点

设计评审时优先看：

- 变化是否局限在正确层级。
- API 契约是否稳定且类型明确。
- 外部依赖失败时主流程是否可控。
- 安全、配置、测试是否跟设计一起落地。
- 是否留下了下一次需求会被迫复制粘贴的结构。
