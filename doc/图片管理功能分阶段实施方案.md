# 图片管理功能分阶段实施方案

> 面向「LightAI 苹果智慧果园监测系统」后端（Spring Boot 3.5.16 / Java 17 / JPA+H2 / Knife4j）
> 目标：在现有后端上增量新增「图片上传 → 元数据提取落库 → MinIO 存储 → AI 智能体分析」能力。
> 本方案按 4 个阶段拆分，每阶段可独立编译、独立验证，依赖 `ddl-auto: update` 自动建表，不破坏现有阈值/决策功能。

---

## 一、总体设计

### 1.1 复用与新增

| 类别 | 内容 |
|------|------|
| 复用 | `Result<T>` 统一返回、`spring-boot-starter-data-jpa` + H2、Knife4j 文档、`application.yml` 配置风格、分层包结构 |
| 新增依赖 | `com.drewnoakes:metadata-extractor`（阶段二，EXIF/尺寸解析）、`io.minio:minio`（阶段三，对象存储） |
| 新增包 | `org.example.lightaisoilmoistirrigationbackend.image`（下含 `controller / service / entity / repository`），与现有 `device / threshold` 平级，保持整洁 |

### 1.2 存储策略演进（每阶段在上一阶段基础上叠加）

```
阶段一：本地磁盘 ./data/images/   +  H2 记录基础信息
阶段二：阶段一  +  解析 EXIF/尺寸（2.1 先提取并打印验证；2.2 再扩展字段落库）
阶段三：阶段二  +  同步上传到 MinIO（源为真），下载改走 MinIO 预签名
阶段四：阶段三  +  调用 AI 智能体分析接口，结论落库（接口后续给定）
```

### 1.3 数据模型总览（3 张表，均自动建）

| 实体 | 表名 | 阶段 | 作用 |
|------|------|------|------|
| `ImageFolder` | `image_folder` | 一 | 目录/相册管理（树形：id + parentId + name） |
| `ImageRecord` | `image_record` | 一/二/三 | 图片主记录：路径、大小、类型、元数据、存储位置 |
| `ImageAnalysis` | `image_analysis` | 四 | 分析结果：结论文本、状态、调用时间、原始响应 |

> 图片二进制**不进数据库**：库里只存元信息 + 文件落盘路径/MinIO 对象名；二进制在本地磁盘或 MinIO。

### 1.4 目录结构（新增文件）

```

└── image/

    ├── controller/ImageFolderController.java  # 目录 CRUD
    ├── service/ImageService.java              # 核心：上传编排
    ├── service/MetadataExtractorService.java  # 阶段二：EXIF/尺寸解析
    ├── service/MinioStorageService.java       # 阶段三：MinIO 封装
    ├── service/ImageAnalysisClient.java       # 阶段四：AI 接口抽象 + 占位实现
    ├── entity/ImageFolder.java
    ├── entity/ImageRecord.java                # 含 metadata / storage 字段
    ├── entity/ImageAnalysis.java
    └── repository/ImageRecordRepository.java
    └── repository/ImageFolderRepository.java
    └── repository/ImageAnalysisRepository.java
```

## 二、阶段一：图片上传接口 + 目录管理

**目标**：能上传图片到本地磁盘目录，并用「目录（相册）」归类，提供列表/预览/下载。

### 2.1 新增配置（application.yml 追加）

```yaml
app:
  upload:
    root-dir: ./data/images        # 上传根目录，项目相对路径
spring:
  servlet:
    multipart:
      max-file-size: 10MB          # 单文件上限，可按需调整
      max-request-size: 10MB
```

### 2.2 实体

`ImageFolder`（目录）：`id, name, parentId(可空), createdAt`。
`ImageRecord`（基础字段，阶段一先建这些，后续阶段扩展）：

| 字段 | 说明 |
|------|------|
| id | 主键自增 |
| originalName | 原始文件名 |
| storedName | 落盘文件名（UUID + 扩展名，防重名/中文乱码） |
| relativePath | 相对 root-dir 的路径，如 `2026/09/uuid.jpg` |
| folderId | 所属目录（可空=未分类） |
| contentType | MIME，如 image/jpeg |
| size | 字节数 |
| storageType | `LOCAL`（阶段三起支持 `MINIO`） |
| createdAt | 上传时间 |

### 2.3 核心实现

- `ImageService.upload(MultipartFile file, Long folderId, String remark)`
  1. 校验：非空、`file.getContentType()` 以 `image/` 开头、大小 ≤ 上限。
  2. 生成 `storedName = UUID + 扩展名`；按 `yyyy/MM/` 建子目录落盘到 `root-dir`。
  3. 写 `ImageRecord`（storageType=LOCAL）。
  4. 返回 `Result<ImageRecord>`。
- `ImageService.serveFile(id)`：读本地文件返回 `ResponseEntity<Resource>`（供预览/下载）。

### 2.4 接口清单（Knife4j 标签「图片管理」「图片目录」）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/images/upload` | 上传：`file`(必填) + `folderId`(可选) + `remark`(可选) |
| GET | `/api/images` | 列表：支持 `folderId`、`page`、`size` 分页 |
| GET | `/api/images/{id}` | 详情（元数据） |
| GET | `/api/images/{id}/file` | 预览/下载原始图片（inline） |
| POST | `/api/image-folders` | 新建目录 |
| GET | `/api/image-folders` | 目录树/列表 |
| DELETE | `/api/image-folders/{id}` | 删除目录（同时处理其下图片的 folderId） |

### 2.5 验证清单（阶段一通关标准）

- [ ] 启动 `mvn spring-boot:run`，Knife4j `/doc.html` 能调通 `/api/images/upload`。
- [ ] 文件实际出现在 `./data/images/2026/09/xxx.jpg`。
- [ ] H2 控制台 `image_record` 出现一行，字段完整。
- [ ] `/api/images/{id}/file` 能在浏览器直接预览该图。
- [ ] 新建目录 → 上传时指定 folderId → 列表可按 folderId 过滤。

## 三、阶段二：提取图片元数据（先打印验证 → 再落库）

**目标**：上传时自动解析图片尺寸、格式与 EXIF（拍摄时间、相机、GPS 等），并据此演进：
- **2.1（本次已实现）**：提取 + **打印到日志**，不落库，用于确认能正确解析各类图片。
- **2.2（已实现）**：已把 A/B 类字段落库，C 类领域字段由上传参数填充，D 类为分析预留（见下方实现要点）。

### 3.1 新增依赖（pom.xml，2.1 即引入）

```xml
<dependency>
    <groupId>com.drewnoakes</groupId>
    <artifactId>metadata-extractor</artifactId>
    <version>2.19.0</version>
</dependency>
```

### 3.2 新增 `MetadataExtractorService`（提取核心）

- `extract(byte[] data, String contentType) → ImageMetadataVO`
  - 用 `ImageMetadataReader.readMetadata(...)` 读取全部目录。
  - **尺寸**：优先 `ExifSubIFDDirectory`（EXIF 宽高）→ 回退 `JpegDirectory` → 再回退 `ImageIO.read()`。
  - **格式**：按文件魔数（magic bytes）判定 JPEG/PNG/GIF/BMP/TIFF/WEBP，兜底用 contentType。
  - **相机**：`ExifIFD0Directory` 的 Make / Model。
  - **拍摄时间**：`ExifSubIFDDirectory.TAG_DATETIME_ORIGINAL` → `LocalDateTime`。
  - **GPS**：`GpsDirectory.getGeoLocation()` 取十进制经纬度。
  - 任何单目录解析异常都只记 `warn`，**不抛异常中断上传**，保证健壮性。
- `ImageMetadataVO`：承载上述字段的简单 POJO（含 `toString()`，便于打印）。

### 3.3 在 `ImageService.upload()` 中接入（2.1 仅打印）

- 上传落盘后，调用 `metadataExtractor.extract(bytes, contentType)` 得到 `ImageMetadataVO`。
- 通过 `log.info("【图片元数据】id=... -> {}", meta)` **打印到控制台/日志**（满足「先打印」要求）。
- **暂不写库**，保留 `image_record` 现有字段；待 2.2 再扩展实体并 `save()`。

### 3.4 验证清单（2.1 打印验证）

- [ ] 启动后上传一张手机照片（带 EXIF/GPS）。
- [ ] 控制台日志出现 `【图片元数据】`，且 `width/height/format/cameraMake/cameraModel/dateTaken/gpsLatitude/gpsLongitude` 有合理值。
- [ ] 上传一张无 EXIF 的 PNG：尺寸正常、EXIF 字段为 null、不报错（日志 warn 可忽略）。
- [ ] 上传非图片文件时仍被阶段一校验拦截（contentType 非 `image/`）。

### 3.5 2.2 实现：元数据落库（已落地）

- 扩展 `ImageRecord` 字段，落库 **A 类（基础）+ B 类（采集 EXIF）** 全部列，并**预留 C 类（田块领域）+ D 类（分析就绪）** 列（详见 3.6）；其中 C 类由上传请求参数填充，`ImageMetadataVO` 字段 set 进 `imageRecord` 再 `save()`（接口形态不变）。
- 验证：`image_record` 对应列被填充；`GET /api/images/{id}` 详情可见元数据。
- 此步即原「阶段二通关标准」：`width/height/format/camera_make/camera_model/date_taken` 正确填充，含 GPS 的有经纬度，无 EXIF 的不报错。

### 3.6 面向 AI 分析的「土壤田块图像」领域元数据设计

> 阶段二的元数据不止 EXIF。图像若来自土壤/田块采集、将用于智能分析（如土壤墒情/灌溉决策），还需补充**领域上下文**，否则 AI 看不懂「这张图是哪块地、什么作物、什么状态下拍的」。以下为完整元数据结构（分 4 类），作为后续落库（2.2）与阶段四 AI 分析的字段依据。

**A 类 · 基础文件元数据（系统生成，必填）**

| 字段 | 类型 | 来源 | 说明 |
|------|------|------|------|
| id | BIGINT PK | 自增 | 主键 |
| original_name | VARCHAR | 文件 | 原始文件名 |
| stored_name | VARCHAR | 系统 | UUID 落盘名 |
| relative_path | VARCHAR | 系统 | **路径**（相对 root-dir，如 `2026/09/uuid.jpg`） |
| content_type | VARCHAR | 文件 | MIME |
| size | BIGINT | 文件 | **文件大小（字节）** |
| storage_type | VARCHAR | 系统 | LOCAL / MINIO |
| created_at | TIMESTAMP | 系统 | **上传时间** |
| folder_id | BIGINT | 用户 | 目录归类 |

**B 类 · 图像采集元数据（EXIF 自动提取，可空）**

| 字段 | 类型 | 来源 | 说明 |
|------|------|------|------|
| width / height | INT | EXIF/ImageIO | 像素尺寸 |
| format | VARCHAR | 魔数 | JPEG/PNG/… |
| camera_make / camera_model | VARCHAR | EXIF | 相机品牌/型号 |
| date_taken | TIMESTAMP | EXIF | **拍摄时间**（比上传时间更贴近真实采集时刻） |
| gps_latitude / gps_longitude | DOUBLE | EXIF GPS | **拍摄位置**（十进制，可反查地块） |
| gps_altitude | DOUBLE | EXIF GPS | 海拔（可选） |

**C 类 · 田块领域上下文（上传时由调用方提供，可空，支撑 AI 分析）**

| 字段 | 类型 | 说明 |
|------|------|------|
| plot_code | VARCHAR | 地块/田块编号，建议关联既有「土壤阈值数据库 / CropConfig」 |
| crop_type | VARCHAR | 作物类型（苹果品种等） |
| soil_type | VARCHAR | 土壤类型（砂壤/黏壤/壤土…） |
| growth_stage | VARCHAR | 物候期/生长阶段 |
| irrigation_status | VARCHAR | 灌溉状态：`IRRIGATED` / `DRY` / `RAIN` / `UNKNOWN` |
| sampling_depth | VARCHAR | 采样深度/拍摄位置（地表/根系层…） |
| capture_condition | VARCHAR | 拍摄条件：光照（自然光/阴天/夜间补光）、天气 |
| operator | VARCHAR | 拍摄人 |
| device_id | VARCHAR | 采集设备/固定摄像头编号 |

**D 类 · 分析就绪/结果（阶段四使用）**

| 字段 | 类型 | 说明 |
|------|------|------|
| analyzed | BOOLEAN | 是否已分析 |
| analysis_status | VARCHAR | PENDING/ANALYZING/SUCCESS/FAILED |
| remark | VARCHAR | 备注 |

**落库与接入建议**：
- A、B 类由系统/EXIF 自动产生；**C 类无法从图片提取**，需在 `POST /api/images/upload` 增加可选请求参数（`plotCode`、`cropType`、`soilType`、`growthStage`、`irrigationStatus`、`samplingDepth`、`captureCondition`、`operator`、`deviceId`），由前端/采集端上传时带来。
- **存储形态**：推荐先将 C/D 类作为 `image_record` 的可空列（`ddl-auto:update` 自动加列，简单直接）；若领域字段后续膨胀，再拆为独立 `image_field_context` 表（1:1 关联）。
- **与既有系统联动**：`plot_code` 关联「土壤阈值数据库」中的地块/阈值配置，使阶段四 AI 分析能结合「该地块的适宜墒情阈值」给出灌溉决策，而非孤立看一张图。

## 四、阶段三：存储到 MinIO

**目标**：上传时把图片同步存入 MinIO 对象存储，下载改为走 MinIO 预签名 URL（对象存储为「真源」）。

### 4.1 新增依赖（pom.xml）

```xml
<dependency>
    <groupId>io.minio</groupId>
    <artifactId>minio</artifactId>
    <version>8.5.10</version>
</dependency>
```

### 4.2 新增配置（application.yml）

```yaml
minio:
  endpoint: http://127.0.0.1:9000     # MinIO 服务地址（本地或云）
  access-key: minioadmin
  secret-key: minioadmin
  bucket: orchard-images               # 存储桶，启动时自动创建（不存在则建）
  # 可选：url-expiry-minutes: 60       # 预签名 URL 有效期
```

> 决策点：若你还没有 MinIO，我可顺带给你一份本地 Docker 启动命令（`minio/minio server /data --console-address :9001`）。请在阶段三执行前确认 MinIO 地址/密钥。

### 4.3 扩展 `ImageRecord` 字段

| 字段 | 说明 |
|------|------|
| storageType | `LOCAL` / `MINIO`（阶段三起写入 MINIO） |
| minioObjectName | MinIO 对象名，如 `images/2026/09/uuid.jpg` |
| minioUrl | 持久化（可选）或每次生成预签名 URL |

### 4.4 实现

- `MinioStorageService`：`upload(InputStream, objectName, contentType)`、`getPresignedUrl(objectName, expiry)`、`ensureBucket()`（启动时建桶）。
- `ImageService.upload()` 编排改为：
  1. 落本地（保留作缓存/兜底，可配置是否保留）。
  2. 上传 MinIO，写 `minioObjectName` + `storageType=MINIO`。
  3. 提取元数据（阶段二）。
- `ImageController` 预览接口：若 `storageType=MINIO`，返回 **302 重定向到预签名 URL**（或直接返回带 `minioUrl` 的 JSON，由前端取 URL 展示）。建议：预览接口返回 `Result` 含 `url` 字段（本地时为 `/api/images/{id}/file`，MinIO 时为预签名 URL），前端无感切换。

### 4.5 验证清单（阶段三通关标准）

- [ ] 配置 MinIO 并启动，`ImageService` 启动时自动建桶。
- [ ] 上传后 MinIO 控制台/ `mc ls` 能看到 `images/2026/09/xxx.jpg`。
- [ ] H2 `image_record` 中 `storage_type=MINIO`、`minio_object_name` 有值。
- [ ] 通过预签名 URL 能在浏览器打开图片（验证读权限与签名正确）。
- [ ] 阶段一/二功能不受影响。

## 五、阶段四：调用 AI 智能体分析（接口后续给定）

**目标**：把图片（或其在 MinIO 的 URL/对象名）传给 AI 智能体分析接口，拿到结论并落库。

### 5.1 新增配置（占位，待你给接口后填真实值）

```yaml
ai:
  analysis:
    url: https://<待定>/analyze        # AI 智能体分析接口
    api-key: <待定>
    # 其他鉴权/模型参数按实际接口补充
```

### 5.2 抽象与实现（接口未给前先留可运行骨架）

- `ImageAnalysisClient`（接口）：`AnalysisResult analyze(ImageRecord record)`。
  - 阶段四先用 `PlaceholderImageAnalysisClient`：打印日志 + 返回占位结论，**保证编译通过、可验证流程**。
  - 你给接口后，新增 `HttpImageAnalysisClient`（用 Spring `RestClient`，Boot 3.5 自带）实现真实调用；通过配置切换 Bean。
- `ImageAnalysis` 实体：`id, imageRecordId, status(PENDING/ANALYZING/SUCCESS/FAILED), conclusion, rawResponse, model/provider, analyzedAt, errorMsg`。

### 5.3 接口清单

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/images/{id}/analyze` | 触发分析（建议 `@Async` 异步，先写 PENDING） |
| GET | `/api/images/{id}/analysis` | 查询该图最新分析结论与状态 |

### 5.4 实现要点

- 触发流程：`analyze` → 置 `ANALYZING` → 调 `ImageAnalysisClient.analyze(record)`（传 MinIO 预签名 URL 或对象名，取决于对方接口约定）→ 成功写 `conclusion` + `SUCCESS`，失败写 `errorMsg` + `FAILED`。
- 传参形式待定：可能对方要「图片 URL」（用 MinIO 预签名）或「base64」或「对象名+内部访问」。接口给定后在此对齐。

### 5.5 验证清单（阶段四通关标准，接口给定后补全）

- [ ] 配置真实 `ai.analysis.url` / `api-key`。
- [ ] 调 `/api/images/{id}/analyze` → 轮询 `/analysis` 拿到 `SUCCESS` + 结论文本。
- [ ] `image_analysis` 表记录完整，失败场景有 `FAILED` + 错误原因。
- [ ] 占位实现可随时切回，便于无接口时跑通全链路。

## 八、关键决策点（请在各阶段执行前确认）

1. **目录管理形态**：方案采用「`ImageFolder` 独立表 + 树形目录 CRUD」。若你只想要简单「分类标签字符串」，可简化为 `ImageRecord.category` 字段，去掉目录 CRUD（更轻量）。
2. **阶段三落盘策略**：默认「本地 + MinIO 双写，MinIO 为真源」。也可「只写 MinIO、本地不留」，需确认本地是否还需保留缓存。
3. **MinIO 可用性**：阶段三前请确认 MinIO 地址/密钥（本地 Docker 还是云），我可附启动脚本。
4. **阶段四触发方式**：默认「手动触发 `POST /analyze` + 异步」。若希望「上传即自动分析」，可在 upload 流程末尾挂接（需权衡性能）。
5. **AI 接口契约**：阶段四的入参（URL/base64/对象名）、出参（JSON 结构）、鉴权方式，待你给接口后在此文档补齐。
